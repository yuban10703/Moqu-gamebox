# 墨水屏交互规范（与代码的对应关系）

规范来源：BOOX 官方《墨水屏开发指南》的产品化，加上本项目的实测约束。
每条都标注了它在代码/测试里的落点，避免规范与实现脱节。

| # | 规范 | 代码落点 | 自动化验证 |
|---|---|---|---|
| 1 | 白底深色文字为默认，彩色仅作增强 | `packages/ui/src/styles.css`（`--ink-black/--ink-white`，无彩色） | — |
| 2 | 状态区分不靠浅灰或透明度：用符号 + 线型 + 文字 | 棋盘符号 `○ □ ◼ ▲ △`（`games/sokoban/src/view.ts`）；按钮禁用=点线、走不通=虚线（`styles.css`） | 壳层测试断言提示文本；`eink-guidelines` 人工检查 |

## 具体尺寸基线

- 正文：18 / 22 / 26 CSS px 三档（跟随「字号」设置，写进 `html[data-font-scale]`）；
- 按钮：≥48px；方向盘按钮高度 = `max(48, 字号 × 2.2)`；
- 棋盘格：整数 px，最小 24px；主基线（10.3 吋）下 11×9 棋盘格子 ≥44px；
- 线宽：默认 2px（1px 在墨水屏上容易消失），设置「加粗线条」关闭后降为 1px。

## 明确不承诺

- **不做零残影承诺**：残影与全刷效果必须真机观察（记录到 [A01](A01-device-baseline.md)）；
- **不做像素级局部刷新**：网页与 WebView 只能拿到整屏全刷与应用级模式切换；
- **不把未实现的能力写进界面**：探测不到的能力显示为不可用并给出指引，而不是显示一个点了没反应的开关。

## 布局硬性规则：主操作必须固定在首屏内

**教训（6 寸竖屏实测）**：详情页的「开始新游戏」在 P6Plus（439×847 CSS）上位于 880~940，
而视口只有 847 —— 用户必须先拖动才能开始游戏。同一份代码在 Note X2（1248×903 横屏）上完全正常，
**这类问题只有窄屏才暴露**，所以必须在多设备上验收。

### 做法：`eink-screen--sticky-footer`

```html
<div class="eink-screen eink-screen--sticky-footer">
  <TopBar/>
  <div class="eink-screen__content"> …可滚动的内容… </div>
  <footer class="eink-footer"> …主操作… </footer>
</div>
```

```css
.eink-screen--sticky-footer {
  /* 必须覆盖 .eink-screen 的 flex:1 —— 在列向 flex 容器里 flex-basis(0) 会压掉 height，
     只写 height:100vh 不生效（实测计算高度为内容高度 951px 而非视口 847px）。 */
  flex: 0 0 auto;
  height: 100vh;
  overflow: hidden;
}
.eink-screen--sticky-footer .eink-screen__content {
  flex: 1 1 auto;
  min-height: 0;   /* 不加这行 flex 子项不肯收缩，不会出现滚动 */
  overflow-y: auto;
  display: flex;
  flex-direction: column;
  gap: var(--gap);
}
.eink-screen--sticky-footer .eink-footer { flex: 0 0 auto; margin-top: 0; }
```

已应用：游戏详情页、帮助页、诊断页（诊断页的原始转储可达 1884px，原本把按钮顶到屏幕外）。

### 自动审计

用 `tools/scripts/` 下的思路（临时脚本，逻辑见提交说明）逐个页面检查
「是否有按钮 bottom > innerHeight」，两台设备都应为 0。
当前结果：Note X2 六页全为 0；P6Plus 首页/设置/帮助/诊断/测试页为 0，
详情页仅剩关卡选择等**滚动区内的次级控件**（主操作已固定）。

### 关卡列表：按实测容量决定是否分页

**规则**：装得下就全部列出、**不显示分页**；装不下才分页，且**翻页按钮固定在页脚**、
无需滚动即可看见。

实现（`GameDetailScreen`）：

- `useLayoutEffect` 里实测三个几何量：列表首项高度、`rowGap`、`gridTemplateColumns` 的列数，
  再用「内容区底边 − 列表顶边」得到可见高度 → 算出能放几行 × 几列 = 容量。
- `关卡数 ≤ 容量` → 每页 = 全部、`pagerNeeded=false`（不渲染分页器）。
- 否则 → 每页 = 容量，并把分页器渲染在**固定页脚**里（与主操作同一栏，窄屏自动换行）。
- 分页器出现后内容区变矮，`content.bottom` 自动上移 → 依赖 `pagerNeeded` 触发一次重算即收敛。
- 容量随视口/字号/粗线设置变化重算；页码越界时夹紧（从第 2 页切回单页不会卡在空页）。

实测（16 关）：

| 设备 | 视口 | 本页显示 | 分页器 | 翻页按钮 |
|---|---|---|---|---|
| Note X2 | 1248×903 | **16（全部）** | 无 ✓ | — |
| P6Plus | 439×847 | 10 | 有 | bottom 830 ≤ 847，**无需滚动可见** ✓ |

规律：**列数由宽度决定、行数由高度决定**，所以横屏大屏一屏放得下 16 关就不分页，
窄屏竖屏放不下才分页 —— 同一份代码自适应，不写死每页数量。


## 游戏页：控制区永不滚动（实测自适应）

**问题**：竖屏（439×847）下「撤销 / 重新开始 / 菜单」位于 844~904，**完全在屏幕外**，
必须拖动才能操作 —— 而这一页恰恰是最不能滚动的（正在玩）。

**根因不是样式，是布局预算与真实 DOM 不一致**：
`computeRootLayout` 把统计栏高度算进了控制区（`controlsHeight` 含 `statsHeight`），
但 `StatBar` 实际渲染成棋盘**上方的一个独立兄弟节点** —— 同一块高度被算了两次（52px）；
再加上方向盘的实测高度是 160px 而预算只给了 120px，累计超出视口 69px。

**修法：不再依赖公式推算，改为结构自适应**

```css
.eink-screen--game {
  flex: 0 0 auto;   /* 必须覆盖 .eink-screen 的 flex:1，见下方陷阱 */
  height: 100vh;
  overflow: hidden;
}
.eink-screen--game > * { flex: 0 0 auto; }            /* 其余一律不缩 */
.eink-screen--game .eink-board-area {
  flex: 1 1 auto; min-height: 0; overflow: hidden;     /* 只让棋盘区收缩 */
}
```

棋盘格子尺寸不再取推算值，而是**实测棋盘区盒子**后用 `computeBoardLayout` 反算
（`ResizeObserver` 跟随尺寸变化）。这样无论以后加了多少行、字号怎么变，
最坏情况是棋盘变小，而控制区永远在首屏内。

## 陷阱：`.eink-screen` 的 `flex: 1` 会压掉 `height`

这个坑**已经踩到两次**（详情页、游戏页）：`.eink-screen` 带 `flex: 1`，
其 `flex-basis: 0` 在列向 flex 容器里优先于 `height`，
所以只写 `height: 100vh` 不生效 —— 页面会跟着内容长高（实测 963px > 视口 903px），
于是"没有收缩的必要"，按钮照样被顶出屏幕。

**凡是需要固定视口高的页面，都必须同时写 `flex: 0 0 auto`。**

## 逐界面审计（两台设备 × 10 个界面）

审计脚本检查每个界面上「有没有按钮 bottom > innerHeight」。当前结果：

| 界面 | Note X2（1248×903） | P6Plus（439×847） |
|---|---|---|
| 游戏页 / 暂停遮罩 / 菜单弹窗 / 过关面板 | 0 屏外 | 0 屏外 |
| 首页 / 设置 / 帮助 / 诊断 / 刷新测试 / 详情页 | 0 屏外 | 0 屏外 |

页面总高也都等于视口高（不再出现"可滚动但看不出为什么"的页面）。


## 竖屏下的控制区布局

竖屏（439 CSS 宽）与横屏的可用空间结构完全不同，因此控制区按方向分别处理：

| | 横屏 | 竖屏 |
|---|---|---|
| 控制区排列 | 一行：方向盘靠左、操作靠右（`space-between`） | **两段居中**：方向盘在上、操作在下，均水平居中 |
| 方向盘中心 | 靠左（116 / 屏宽 1248） | **与屏幕中心重合（偏差 0）** |

改为竖屏居中的原因：竖屏宽度只有 400 多，`space-between` 会把方向盘挤到最左、右侧留一大片空白，
而且拇指够不着对侧。用 `@media (orientation: portrait)` 只在竖屏生效，横屏不受影响。

## 状态条：压缩成一行

`.eink-statusstrip` 从两行 84px 压到**一行 44px**（提示与保存状态并排、超长省略）。
省下的 40px 直接变成棋盘高度：竖屏棋盘 363 → **403**，横屏 489 → **529**。

例外：**保存失败**时该行需要「重试 / 导出」按钮，此时 `data-expanded="yes"`
放开换行、恢复自适应高度 —— 绝不能为了省高度把出错时的操作按钮挤没。

### 高度必须用 `height`，不能用 `min-height`

用户反馈「这个方向走不通的提示出现时会导致棋盘移动」。实测转场：

```
提示清空后:  状态条 44px, 棋盘区 355, 棋盘 top 216
提示出现后:  状态条 46px, 棋盘区 353, 棋盘 top 215   ← 棋盘被顶上去 1px
```

根因：提示那一行的实际高度是 **46px**（22px 字号 × 1.5 行高 + 边距），
`min-height: 44px` **拦不住它** —— 状态条长高 2px，棋盘区被挤小 2px，
而棋盘在区域内居中，于是整体上移 1px。文案更长（换行）时位移会更大。

修法：状态条改为**固定高度**（`height/min-height/max-height` 都是 48px）+ `overflow: hidden`，
内容多寡都不允许改变高度。修复后转场实测**完全一致**（状态条 48、棋盘区 351、棋盘 214 均不变）。

**规则：任何会在游玩过程中出现/消失的元素（提示、保存状态），其高度都必须恒定。**

### 同类风险排查

- **统计栏**（`.eink-stats`）默认 `flex-wrap`，行数会随数值宽度变化 —— 确实发生了：
  竖屏下开局「用时 0:00」能挤在一行，涨到 `0:07`/`1:23` 后把「用时」挤到第二行，
  统计栏长高一行，棋盘被顶动（用户实测反馈）。
  **修法**：游戏页给统计栏**固定列数**（`StatBar columns={...}`），
  竖屏 2 列、横屏一行 → 行数与数值宽度无关，高度恒定。
  实测：把「用时」改成 `12:34` 后统计栏与棋盘的位置**完全不变**（竖屏 84px / 横屏 36px）。

  > 已按此优化：删掉了统计栏里冗余的「关卡 12/16」（标题已写「第 N/M 关」），
  > 竖屏 3 项排一行（36px），棋盘从 351 → **386**。
  > 横竖屏的列数上限都取 3，行数因此恒定且最少。
- **保存失败**行会展开（`data-expanded`），此时棋盘位移是可接受的：出错信息与重试按钮必须让用户看到。


## 棋盘纹理（墙壁 / 箱子 / 角色）

目标是让棋盘更好看，同时**不使用灰度**（快刷是 1-bit，灰阶靠抖动，运动中会被压平或起噪点）。
全部用内联 SVG 与纯黑白纹理实现：

| 元素 | 画法 | 状态区分 |
|---|---|---|
| 墙壁 | 棋盘容器上的 45° 斜纹（`repeating-linear-gradient`） | 非墙格铺白遮住纹理 |
| **箱子** | **占满整个格子**的板条箱：外框 + 对角线交叉 | 空心＝未就位；**实心 + 白斜线＝已就位** |
| 角色 | 人形剪影（头 + 肩） | 普通＝剪影；**在目标点上＝目标圆环 + 缩小的剪影** |
| 目标点 | 圆环 | — |

两个实现要点：

1. **斜纹画在棋盘容器上、墙格留空**，而不是每格画一份：
   渐变在每个元素里都从头开始，逐格绘制会在格子交界处出现错位接缝。
2. **箱子占满格子**（尺寸 = 格子 − 两侧边框，实测占 93%~95%）：
   留白会让箱体和通道混淆；占满后「箱体 / 可走通道」一眼可分。

### 已知取舍：抗锯齿灰边（经用户确认接受）

对角线与人形曲线会**抗锯齿**，棋盘区约 **0.2%~0.5%** 的像素是中间灰
（实测 P6Plus 0.53%，Note X2 基线 0.23%）。
在 1-bit 快刷下这些边缘会略显粗糙。

曾实现过一版**完全锐利**的方案（砖块图案墙 + 全轴对齐矩形像素画，
`shape-rendering="crispEdges"`），实测棋盘区灰像素降到 **0.00%~0.01%**；
但用户更喜欢当前这版的观感（斜纹墙 + 圆环 + 人形），因此保留当前方案。
若将来需要极致锐利，可回到那套像素画实现。

另：「加粗线条」设置会同时加粗字形描边与墙面斜纹。

### 踩到的坑：背景图块不要用非整数尺寸

锐利版曾用 `background-size: calc(var(--cell) * 0.45)`（= 31.05px）缩放 SVG 图块，
结果整个砖墙落在非整数设备像素上被糊成灰 —— 棋盘区灰像素从 0.17% **恶化到 4.16%**。
**结论：背景图块要用固定整数尺寸**，并让尺寸在两个 dpr（1.5 / 1.875）下都是整数设备像素
（即取 8 的倍数）。


## 游戏页标题：承载原本放在统计栏里的信息

删掉「关卡 12/16」后，这部分信息移到标题与副标题（TopBar 本来就支持副标题）：

| 位置 | 内容 | 示例 |
|---|---|---|
| 标题 | 游戏名 · **第 当前/总数 关** | `推箱子 · 第 15/16 关` |
| 副标题 | 难度 · 已过关进度（无进度时只显示难度） | `挑战 · 已过关 3/16` |
| 统计栏 | 只留与操作直接相关的项 | 步数 / 推箱次数 / 用时 |

- 标题新增文案 `sokoban.level.position`（`第 {index}/{total} 关`），保留旧的 `sokoban.level.label`。
- 副标题进度文案 `shell.game.cleared`（`已过关 {done}/{total}`）；
  `done` 为 0 时自动省略该段，避免出现「已过关 0/16」这种噪音。
- 统计栏项数从 4 降到 3，横竖屏都能排成一行（36px），行数恒定。


## 游戏卡片网格：列宽决定一屏能放几款

用户实测反馈「首页全部游戏需要滑动才能看全」，根因有三条，缺一不可修：

| 问题 | 修复 |
|---|---|
| `.eink-grid` 最小列宽 220px，439 宽竖屏（内容约 415px）下 `auto-fill` 只能算出 **1 列** | 降到 **180px**，同宽度下得 2 列 |
| 卡片竖排三行 + `min-height:140px`，4 张就要 596px | 改**两行网格布局**（图标+标题一行、进度一行），`min-height:92px` |
| 首页没有固定页脚（其它页面有），页脚被列表顶出屏幕 | 首页改用 `eink-screen--sticky-footer` + `.eink-screen__content` |

另外把 `auto-fill` 换成 `auto-fit`：`auto-fill` 会保留空轨道，宽屏上 4 款游戏会挤在最左
（实测 1248 宽下解析出 6 条轨道只占 4 条）；`auto-fit` 折叠空轨道，卡片按实际数量铺满一行
（同样宽度下卡片从 186px 变 285px）。

修复前后实测（439×847 竖屏）：

| 指标 | 前 | 后 |
|---|---|---|
| 网格列数 | 1 | **2** |
| 页面总高 | 1009（视口 847） | **847 = 视口** |
| 页脚位置 | 937–997（屏外） | **775–835（屏内）** |
| 卡片 | 415×140 ×4 行 | **202×92 ×2 行** |

> 经验：**窄屏上的多列网格，最小列宽要按最窄目标视口倒推**（439px 屏减去内边距后约 415px，
> 两列要求 `2 × min + gap ≤ 415`，即 min ≤ 200）。220px 这种「看起来不大」的值在手机上就会退化成单列。
> 同时保留量要留出余量：当前 4 款两行；按这个尺寸 8 款也能一屏放下（4 行 ≈ 745 < 847）。


## 棋盘线宽层次：靠线宽建立结构，不靠灰度

黑白屏上区分「格子 / 分组 / 边框」只能用线宽与形状。数独的 9×9 如果所有线一样细，
3×3 宫的结构就完全看不出来（用户实测反馈「线条粗细要明确一下」）。

约定（实现见 `styles.css`，用户最终确认的取值）：

| 层级 | 线宽 |
|---|---|
| 格子线 | **1px** |
| **分组线**（如数独 3×3 宫） | **5px** |
| 棋盘外框 | **5px** |

真机实测（`加粗线条` 为 on 时）：P6Plus 细 0.53px / 粗 4.8px，Note X2 细 0.67px / 粗 4.67px —— 比例约 **9:1**。

- 棋盘线**不跟随「加粗线条」设置**。该设置只影响字形笔画与界面控件边框（`--line`）。
  原因：若格子线跟着设置走，加粗模式下格子线变 2px、与分组线只剩 2 倍差距，层次立刻消失。
- 外框**不得细于分组线**，否则棋盘看起来是散的。
- 分组由游戏声明：`BoardView.groups = { cols: 3, rows: 3 }`，
  壳层在组边界给格子打 `data-sep-right` / `data-sep-bottom` 并加粗对应边框。
  相邻格自身的 1px 会叠加上去，所以视觉宽度约比设定值再多 1px。
- 数字类玩法（数独）字号取格子边长的 **0.66**（原先 0.62），加粗 700。

### 顺带清掉的冗余统计

数独原先把「已填 45/81」「总格数 81」「空格 36」并排显示，但：
总数已含在分母里；空格数 = 81 − 已填，是同一信息。三项让统计栏多占一行（窄屏上直接压缩棋盘）。
精简为「已填 x/81」一项后，竖屏棋盘 **368 → 413px**、格子 40 → 45px、数字 26.4 → 29.7px。

> 判据：**同一指标的不同表述不算两个指标**。窄屏上每多一项都可能多占一整行。


### 状态区分：数量多的格子不要用边框

数独里「题目给定」与「玩家填入」必须能分辨。最初的实现给给定格加了
`box-shadow: inset 0 0 0 2px`，但它**叠在格子自身的边框上**（2px + 2px = 4px），
45 个给定格全部变粗，整块棋盘显得很重（用户反馈「已有数字的方块还是太粗了」）。

改为只靠**字重**区分，不动边框：

| 格子 | 边框 | 字形 |
|---|---|---|
| 题目给定 | 与所有格子一致 | `font-weight: 800` |
| 玩家填入 | 与所有格子一致 | `font-weight: 400` |

> 判据：**一个界面上大量重复出现的元素，不应各自再加边框**——
> 边框是「结构」信号，重复几十分会变成噪声；状态差异优先用字重、填充、符号表达。
> 边框只留给少量、稀疏的元素（例如当前选中格）。

最终取值是**字号 + 字重双重区分**（由游戏自己声明，壳层不写死）：

| 格子 | 字号（相对格子边长） | 字重 |
|---|---|---|
| 题目给定 | 0.74 | 800 |
| 玩家填入 | 0.50 | 400 |

字号通过 `CellView.textScale` 由游戏声明（缺省 0.66）。为什么不让壳层按 `kind` 写死：
`tile` 这个 kind 2048 也在用（它的数字应当保持大），写死会误伤别的玩法。
真机实测：P6Plus 给定数字 34.0px / 玩家填入 23.0px；Note X2 给定 50.3px / 玩家填入 34.0px。

> 1px 细线在 dpr 1.875 的机器上会被吸附成**单个设备像素**（实测 1px → 0.53 CSS px），
> 竖线在面板上很淡。当前是用户确认的取值；若觉得太淡，**2px 是「看得见的最细」起点**。
