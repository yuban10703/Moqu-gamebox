# 备份与存档安全检查（2026-10-07）

本次针对不可信备份文件、跨端存储和 Android 文件读取入口检查并修复问题。
以下 Medium 是按本项目的可用性和数据完整性影响评估，未经正式 CVSS 评分；没有确认可利用的 High 问题。

## 已修复的问题

### Medium：备份导入的资源消耗没有边界

Web 在检查前完整读取文件，Android 在主线程 `readText()`，JSON 校验还会递归遍历任意深度。
用户导入恶意文件时，可能出现内存消耗、界面阻塞或栈溢出。回归用例用 12,000 层嵌套复现了未捕获的 `RangeError`。

现在 Web 在读取前按文件大小拒绝超过 16 MiB 的文件，Android 在后台线程按实际读取字节截断，最多额外读取一个字节。
核心解析层在校验和计算之前检查字节、深度（64）、节点（500,000）、存档数量（256）与成绩记录数量（10,000）。
拒绝的文件不会进入持久化流程。Web 文件读取失败也会显示错误。

### Medium：畸形备份字段可持久化并破坏后续界面或导出

旧解析器只检查部分信封字段。带合法校验和的 `progress.completed = {}` 可以写入存档，
但首页、详情和通关逻辑会把它当作数组使用；`records = [null, null]` 可写入并导致记录排序报错。
校验和用于发现损坏，不是认证机制，攻击者能自行重算。

现在检查会话、计数、进度数组、成绩映射与完成记录的字段类型；过滤不合法的单游戏设置；
拒绝重复游戏 ID；读取本地记录时忽略已有的损坏项。仍保留旧设置字段的兼容解析和坏存档提示。
规范序列化使用没有原型的对象，不再漏掉 `__proto__` 属性；不可信 JSON 的该键在结构检查时被拒绝。

### Medium：覆盖和恢复失败可能删除当前存档或覆盖保留副本

旧导入与恢复实现先删除 committed，再写新数据。磁盘不足或写入异常可让当前进度消失，
残留 pending 还可能在下次恢复时应用一次已报告失败的替换。相同时间戳的多次 keepBoth 导入会复用备份键。

现在替换使用 committed 上的原子 CAS，不先删除当前存档，也不为失败替换留下 pending。
keepBoth 先按原始文本原子预留一个未使用的备份键，再替换当前值；提交编号持续递增，
阻止导入前的旧会话写回。单个存档替换失败会返回错误，不再被汇总为导入成功。

整个备份中的多个游戏、设置与成绩不是一个跨项事务：前面已成功导入的项目不会因后续失败而整体回滚。
