## 诚实边界

- 本机没有安装浏览器（也无 KVM/模拟器），因此**没有自动化视觉回归**：
  布局正确性靠纯函数不变量测试保证，视觉可读性必须真机判断；
- 桌面截图或模拟器通过**不算**完成（与规划的阶段完成条件一致）；
- 未实测的能力不作为宣传或承诺依据：见 [eink-guidelines](eink-guidelines.md) 与
  [refresh-adaptation](refresh-adaptation.md) 的「明确不承诺」。

## 网页版冒烟测试（真实浏览器）

真机与浏览器是**两条不同的运行路径**，必须分别验证：

| | 真机（BOOX WebView） | 网页版（浏览器） |
|---|---|---|
| 存储 | 原生 SQLite（`storage kind = android`） | **IndexedDB**（`storage kind = indexeddb`） |
| 刷新能力 | Onyx SDK（全刷可用） | **无**（`onyxSdkFound = false`，如实上报） |
| 语言 | 跟随系统 | **跟随浏览器语言** |
| 屏幕 | 固定设备视口 | 任意视口 |

这些差异在 jsdom 单测里覆盖不到（jsdom 没有真实 IndexedDB 与真实布局），
因此用 Playwright + Chromium 做了真实浏览器冒烟测试。

### 运行方式

```bash
npm run build:web                       # 构建产物
npm run serve:web &                     # 静态服务 → http://127.0.0.1:8899/
# 首次需要装浏览器（装到 gitignored 的 .toolchain/pw，不入项目依赖）
mkdir -p .toolchain/pw && cd .toolchain/pw && npm i playwright \
  && npx playwright install chromium && npx playwright install-deps chromium
npm run smoke:web                       # 运行冒烟测试
```

### 覆盖与结果（25/25 通过）

- 首页 / 详情页 / 游戏页渲染；`platform.kind = web`、`storage.kind = indexeddb`
- **不谎报 BOOX 能力**：网页版 `onyxSdkFound = false`
- 方向键可操作，步数递增（0 → 6）
- 存档提交：界面显示「已保存」，且 **IndexedDB 中 `loadResult() = ok`、存档步数与界面一致**
- **刷新后存档恢复**（6 → 6）
- **语言跟随浏览器**：`locale=en-US` 时界面为英文
- **两种视口逐页断言「主操作都在首屏内」**：1248×903 与 439×847，
  首页/详情页/游戏页均 0 个屏外按钮；统计栏行数固定为 1

- **离线能力**（Service Worker）：
  SW 注册并激活（`activated`）、资源预缓存 5 条、**断网后重载仍能打开应用**、
  状态显示「已可离线」、**离线时存档仍可读**（步数一致）

截图：`docs/screens/web-01-landscape-game.png`、`web-02-portrait-game.png`

### 过程中踩到的两个坑（脚本自身）

1. **语言**：无头浏览器默认 `en-US`，界面走英文，最初按中文文案断言导致超时 ——
   这反而验证了「语言跟随浏览器」这条行为。测试里显式指定 `locale` 才稳定。
2. **API 名字**：`saves.load()` 返回存档或 null，`saves.loadResult()` 才返回 `{status, envelope}`；
   用错方法会得到 null 而非报错，断言会假失败。
3. **不要在脚本里用 `URL` 作局部变量名**：它会遮蔽全局 `URL`，
   使 `new URL(..., import.meta.url)` 抛 `Cannot access 'URL' before initialization`。
   （同一个坑在 smoke 与临时脚本里各踩了一次，第二次才意识到是同一个原因。）

### 本地访问提示

- 静态服务用**托管后台任务**启动，避免随会话结束被回收：`npm run serve:web`
- 服务监听 `0.0.0.0`，容器内 `http://127.0.0.1:8899/` 与容器 IP 均可访问。
- 若浏览器在**容器外**（例如 GUI 是 `127.0.0.1:3080` 通过端口映射进来的），
  则只有被映射的端口可达，`127.0.0.1:8899` 会「拒绝连接」；
  此时用容器 IP（`hostname -I` 的第一个地址）访问。

## 探索式缺陷探测（主动找 bug，而不是等用户报）

把「用户实际报过的缺陷类型」固化成可重复断言，主动去撞问题：

```bash
npm run build:web && npm run serve:web &   # 前置
npm run explore                            # 两个套件一起跑
```

| 套件 | 覆盖 | 当前结果 |
|---|---|---|
| `tools/scripts/explore-ui.mjs` | 横竖屏中途切换、暂停/恢复、重开确认、退出后继续、真实通关（推箱子见证步）、菜单弹窗、难度切换、设置项（含字号三档）、键盘操作 | **75/75** |
| `tools/scripts/explore-data.mjs` | 备份导出（下载 + JSON 结构 + 校验和）、导入非法备份、**存档被截断后的恢复入口**、多游戏进度、继续卡片指向、清空全部进度 | **9/9** |

每步都检查四类不变量：**没有不可达按钮**（可滚动容器内的除外）、**固定页脚在屏内**、
**没有缺键 ⟦key⟧ 标记**、**页面不溢出视口且棋盘未被裁切**。任何页面 JS 错误都会让退出码非 0。

### 本轮因此发现并修复的 4 个真实缺陷

1. **「返回游戏库」其实只到详情页** —— 顶栏返回与浮层里的「返回游戏库」共用了同一个 `goBack`，
   文案与行为不符。现在 `GameScreen` 区分 `onBack`（回详情）与 `onExit`（回游戏库）。
2. **设置页在字号「大」时溢出视口**（实测 930 > 847）——「清除全部进度」被顶出屏幕。
   设置页是唯一没用 sticky-footer 模式的页面，已补齐（内容滚动 + 页脚固定）。
3. **「继续上一局」不跟随最近游玩** —— 原用 `entries.find(...)`，按注册顺序取第一个有存档的，
   于是玩了 2048 后首页仍显示推箱子。改为按 `updatedAt` 取最近的。
4. **已提交的存档损坏时被静默忽略**（最严重：用户会无声丢档）
   - `recover()` 原先只扫 `pending` 键 → 新增扫描 `committed` 键，把无法校验的上报为
     `RecoveryReport.corrupt`，且**不删除**数据（删掉等于替用户丢档）。
   - `saves.list()` 原先遇到连 meta 都解析不出的条目**整条跳过** → 改为用 key 里的 gameId
     上报为 `corrupt: true`，首页据此显示「存档已损坏…原文件会原样保留，建议先导出备份」并给出恢复入口。
   - 新增 3 个回归测试（损坏的已提交存档被上报且不删除 / 健康存档不误报 / 截断成垃圾仍能上报）。


## 黑白棋（Reversi）—— 第 5 款游戏

选择它的理由：**1-bit 墨水屏的理想玩法** —— 黑子实心 `●`、白子空心 `○`，完全不需要灰度或颜色；
8×8 在 439px 竖屏上格子 50px（远高于 24px 下限）。

- 规则层 `reduce` 内**自动完成白方应手**（含过手），壳层完全不感知 AI；不变量：
  **非终局状态下必定轮到黑方且黑方有棋可下**（`decode` 据此拒绝不一致的存档）。
- 三档难度：`starter` 种子随机 / `skilled` 角位加权贪心 / `challenging` minimax(2~3 层 + α-β)。
  24 种子对局白方总分 16 / 20 / 24（满分 24），challenging 单次应手 ~2–3ms。
- 撤销粒度是**一整回合**（玩家 + 对方），撤销后重下同一手得到完全相同的局面。
- 呈现：棋子 `tile` + `●`/`○`，合法落点 `number` + `·`（`textScale 0.5`），无分组线，统计三项。
- 真机（P6Plus）：64 格 @50px、棋盘 410×410、开局恰好 4 个落点提示、点一下后黑 2→3 白 2→3（AI 已应手）、屏外按钮 0。

## 本轮由「新游戏接入」暴露出的 4 个壳层缺陷

1. **`lost` / 平局终局没有任何结果 UI** —— `session.solved` 恒等于 `status === 'won'`，
   而结果面板只认它。于是扫雷踩雷、黑白棋输棋后玩家看不到任何终局反馈。
   → 新增 `session.finished`（非 playing），结果面板与计时停止都改用它；`solved` 仍只管「过关」与进度记录。
2. **「下一关」按钮永远禁用** —— 按钮查的是 `id === 'next-level'`，而**没有任何游戏声明这个控件**，
   于是推箱子过关后也点不动。→ 让游戏按契约声明 `next-level`（推箱子已声明，最后一关 `enabled:false`），
   不由游戏声明时该按钮**不渲染**（无关卡玩法不再显示一个永远灰着的按钮）。
3. **控制区重复出现「下一关」** —— 修 ② 时 game 声明的 action 控件被当成自定义按钮又渲染了一遍。
   → 壳层自有控件 id 集合补上 `next-level`。
4. **WebView 重载后按返回会跳回重载前的页面**（崩溃自愈正是主动重载的场景）
   —— 重载会复用同一条历史记录并保留其旧 `screen` state，而应用启动时显示首页；
   于是「首页 → 设置 → 返回」会突然落回一个旧游戏页。
   → 首次加载给历史项打 `loadId`，popstate 只信任本次加载压入的项，陈旧项一律回首页。


## 第 6 款游戏：数字华容道（15-puzzle）

| | |
|---|---|
| 包 | `packages/games/fifteen`（75 个测试） |
| 难度 | 3×3（8 数码）/ 4×4（经典 15 数码）/ 5×5（24 数码） |
| 可解性 | **构造性保证**：从已还原局面做 60/120/200 步随机合法滑动（每步排除上一步反向）；结果若仍是还原态则换随机流重打 |
| 独立验证 | 测试用与实现无关的逆序数奇偶性判据（偶数宽度含空白行）对 3 档 × 40 个种子逐个判定可解 |
| 动作 | `slide`（方向键语义 = 空白格朝该方向移动）、`tap`（点相邻块滑动，非相邻返回 null）、`undo`、`restart` |

## 本轮修掉的 4 个问题（2 个由测试逼出来）

1. **存档耐久性：防抖窗口会丢最后一步**（真实风险：WebView 崩溃自愈就是主动重载）
   → 去掉 500ms 防抖，改为**每步立即提交**；用「串行 + 最新覆盖」队列避免并发提交，
   **提交前用最后成功提交的 commitId 重新盖章** —— 否则连按方向键时多个副本带同一 commitId，
   第二份起会被 CAS 判成 conflict，出现「界面在前进、存档却停在旧状态」（UI 测试直接抓到了这个冲突）。
2. **恢复存档后「用时」被清零**：界面显示的是 `elapsed - levelStart`，而加载时把两者都设成已保存值，
   差值恒为 0 → 重开应用后计时看起来归零。
3. **方向键动作名不统一**：壳层固定派发 `{type:'move',dir}`，而新玩法的规范动作是 `{type:'slide',dir}`。
   → 壳层改为**优先走 `controlAction('move-<dir>')`**，游戏未映射时回落到 `{type:'move',dir}`
   （老游戏一行都不用改）；数字华容道补上映射，真机/浏览器验证「按左 → 步数 1」。
4. **探索套件不可重复运行**：其中一步会故意截断存档验证恢复入口，却不清空 → 下次运行读到上次的坏档，
   把测试自己制造的损坏误判成「用户进度丢失」。→ 三个套件统一在开头清空存储。

### 未结项（下一轮继续）

`tools/scripts/explore-flows.mjs` 的第 3、4 步断言仍不稳定：
第 3 步「重载后用时延续」与第 4 步「切游戏再回来进度仍在」在**连续硬重载 + 快速恢复**的序列下不通过。
已确认**不是**应用缺陷（用最小复现脚本逐步 dump 存档：每一步 `loadResult` 都是 `ok`，
存档内容与预期一致；之前的「存档已损坏」是套件上一轮自己制造的残留）。
更像是测试在「重载后恢复到哪一局 / 何时读计时」上的假设不成立，需要在下一轮把这两步改成
**以存档内容为准**的断言，而不是以界面文案为准。


## 第 7 个真实缺陷：填错一个数字后存档再也打不开（本轮）

**现象**：在数独里填入一个「不冲突但错误」的数字（数独的正常玩法），
之后重开应用/回到该局时提示「存档已损坏 本次进度无法持久化」—— 用户再也打不开自己的进度。

**定位过程**（探索式测试 → 最小复现 → 单元级验证）：
1. 流程套件在「切游戏再回来」后报「存档已损坏」；先怀疑是自己的测试残留，逐条 dump 存档排除；
2. 最小复现确认：存档在存储里是好的（`loadResult` = ok、`moves:2`、`filled:46`），
   但**加载时被判为损坏**；
3. 把真实存档的 `state` 原文喂给 `sudokuGame.decode()` → 抛
   `sudoku.illegal.state:wrong-digit:0` —— 根因确定。

**根因**：数独的 `decode` 里有一条「玩家填入必须等于解」的校验。
但规则层允许填一个不冲突的错误数字（`status` 才用它判断对错），
于是**游戏自己产生的合法状态被自己的 decode 拒绝**。

**修复**：删掉该条校验（正确性判定交给 `status`/`view`）。
新增回归测试「填入合法但错误的数字后存档仍可加载」。

**放大检查**：这类缺陷是**一类**问题，因此加了跨全部游戏的通用契约测试
`packages/ui/test/games-contract.test.ts`：对 6 款游戏 × 各档难度随机走 60 步合法动作，
**每一步之后 encode → decode 都必须成功且往返一致**。6 款全部通过 → 数独是唯一实例。


## 第 8 个缺陷：旧规则版本的存档被笼统提示为「存档已损坏」

**问题**：`rulesVersion` 与当前游戏不一致时（规则升级后的旧存档），
会话层把它和真正的数据损坏归为同一状态，界面统一显示「存档已损坏」——
但两者对用户的意义完全不同：一个是数据坏了，一个是「这份进度来自旧版本规则」。

**修复**：会话层新增 `corruptReason`（`corrupt` | `unsupported-version`）：
- 存档读取返回 `reason === 'unsupported-version'` → 记为版本不支持；
- 加载时 `existing.rulesVersion !== game.rulesVersion` → 记为版本不支持（而不是损坏）。

界面按原因切换标题与说明，新增中英文案 `shell.storage.unsupportedHint`：
> 这份存档来自旧版本的规则，当前版本无法继续。原文件会原样保留，建议先导出备份。

**测试**：新增用例「规则版本落后的存档提示『版本不受支持』，而不是笼统的『存档已损坏』」——
用 `reseal` 构造一份**校验和与 schema 都有效、只有 rulesVersion 落后**的存档，
断言界面出现 version 文案且**不出现** corrupted 文案。

**顺带澄清**：这类存档**不会**进首页的「存档自检」入口 ——
它的 schema 与校验和都有效，`readMeta` 认为它是正常存档；
只有加载时比对规则版本才会发现落后。这也是为什么该用例必须走「详情 → 继续」而不是自检入口。

## 备份闭环：导出 → 再导入（本轮补上的盲区）

此前只测过「导入非法文件会明确报错」，**从没测过把自己导出的备份再导入回去** ——
而备份正是用户的安全网，这条闭环必须可验证。

新增用例（tools/scripts/explore-data.mjs，第 1b 节）：
1. 用上一节导出的 JSON 文件喂给导入入口；
2. 断言**不出现「导入失败」**；
3. 断言 `save:1:committed:*` 集合不变（只比 committed，不含备份键）；
4. 断言**导入前保留了旧档备份**（`save:1:backup:*` ≥ 1 份）；
5. 断言导入后存档内容仍可读（sokoban moves 值）。

第 3 条初版写成"所有键集合不变"，实测为 `1 → 2` 而失败 —— 排查看出多出来的是
`save:1:backup:*`，即**导入在覆盖前会先留一份旧档**，是刻意的安全设计而非缺陷。
断言据此改成「committed 不变 + 备份存在」，把这条行为也纳入保护。

## 真机审计脚本的退出码（本轮修掉的验证链软环节）

`tools/device/audit-games.py` 此前**只打印结果、永远返回 0** ——
而它是 `verify-device.sh` 的最后一步，于是即使某款游戏越界或出现缺键，
整条真机验收链仍会「通过」✗ 这与之前"断言恒真等于没测"是同一类问题。

现在：收集每款游戏的「屏外按钮 / 缺键 / 结果无法解析」，结束时打印汇总并给出退出码。
两条路径都实测过：
- 正常：退出码 **0**，输出「✓ 9 款游戏全部通过（无屏外按钮、无缺键）」
- 强制触发失败条件：退出码 **1**，逐条列出问题

> 教训一致：**验证工具本身也要能被验证**。凡是"只会打印、不会失败"的检查，
> 在链路上都等于不存在。

### 接入时处理的一个规则冲突

21×21 在 415px 宽下只有 **19px** 格子（低于 24px 触摸下限），会触发我此前加的「可玩性守卫」。
但迷宫是**方向盘驱动**的，不靠点格子 —— 触摸下限对它不适用。

因此守卫改为**按交互方式区分**：只有当游戏**没有**声明方向盘控件时才要求格子达到触摸下限
（这类玩法靠点格子）。这样 21×21 迷宫合理通过，而点格子的玩法仍被严格守住。

### 顺带放开的壳层能力

`TEXT_KINDS` 增补 `floor`：迷宫用 `floor` + `·` 标记轨迹（推箱子的 floor glyph 为空，不受影响）。
子代理主动报告了这处缺口（"规则层已备好 visited，但壳层不会渲染"），属于好的协作。


## 最受限组合：极矮横屏 + 最大字号（本轮补上）

此前两个套件各测一个维度 —— landscape 用默认字号、maxscale 用 439×847 竖屏 ——

## 第 11 款游戏：关灯游戏（Lights Out）

| | |
|---|---|
| 包 | `packages/games/lightsout`（58 个测试） |
| 难度 | 5×5（打乱 6 步）/ 5×5（12 步）/ 6×6（20 步） |
| 规则 | 点一格翻转它**及其上下左右**（十字，含自身）；全部熄灭即胜 |
| 可解性 | 从"全灭"出发用 `createRng(seed)` 做 N 次十字翻转来打乱 —— **构造性保证有解**，无需求解器 |

**验证亮点（子代理主动做的三重保障）**
1. **构造性**：十字翻转是对合，把打乱步骤原样再走一遍必然回到全灭 —— 这本身就是一条解；
2. **独立判据**：测试里用 **GF(2) 高斯消元**独立判定"是否存在解"并给出解序列，再用规则层翻转验证；
   还加了**区分度测试**（5×5 单灯局面既有有解也有无解）证明判据**不是恒真** ——
   这正是本项目反复强调的"检查必须能失败"；
3. **存档复核**：decode 复算初始谜题 + 校验游标 + 把 history 依次翻转必须逐格等于存档，不可达局面一律拒绝。

浏览器实测（439×847）：25 格 **@81px**、棋盘 415×415、开局 5 灯亮；点中心后亮灯 **5 → 6**（十字翻转生效）、
屏外按钮 0、无缺键。首页现为 **11 款游戏**。

### 顺带验证了 `check:docs` 真的很管用

接入后 `npm run verify` 立刻**失败** —— 原因是交接文档的检查点还写着"10 款游戏"。
这正是第 39 轮加这个守卫的目的：**游戏数变化后忘记同步文档，会当场被拦下**，而不是留着一份说谎的文档。
